# Building Analytics Backend

Persistent backend service and normalized PostgreSQL relational storage engine for Chilean condominium financial reports (*"Informe Gastos Comunes"* and *"Notas de Cobro por Unidad"*).

Built with **FastAPI**, **SQLAlchemy 2.0**, **PostgreSQL 15+ (Google Cloud SQL)**, and **Alembic**.

---

## 🏗️ Architecture Overview

The database uses a 3NF normalized schema designed for financial integrity:
* **`units`**: Master catalog of the 420 apartments, their tower, unit number, and official prorated share (`alicuota` as exact `NUMERIC(8, 5)`).
* **`billing_periods`**: Master time dimension for monthly fiscal cycles (`YYYY-MM-01`).
* **Building Expenses (3-Tier)**: `expense_reports` ➔ `expense_sections` ➔ `expense_items`.
* **Unit Billing Hierarchy**: `unit_bills` ➔ `unit_bill_concepts`, `unit_bill_consumptions` (metered hot water), and `unit_bill_charges` (fines/amenities).
* **Financial Precision**: All CLP amounts are stored as exact integers (`BIGINT` / `INTEGER`) to prevent floating-point drift.
* **Security**: Cloud SQL runs on a **100% Private VPC network** (no public IP).

## 🚀 How to Create Future Database Migrations with `--autogenerate`

Because your Google Cloud SQL database is **100% private** with no public IP, you never connect your laptop to the cloud to create migrations.

Instead, use a **local Docker PostgreSQL container** to let Alembic diff your Python models and automatically generate the migration code for you.

### Step 1: Start a Local PostgreSQL Container
Run a temporary PostgreSQL 15 container on your development machine:
```bash
docker run --name pg-local \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=condominium_db \
  -p 5432:5432 \
  -d postgres:15
```

### Step 2: Bring the Local Database Up to Date
Apply all existing migrations to your local container so it has the current schema:
```bash
alembic upgrade head
```

### Step 3: Modify Your Python Models
Edit `backend/app/models.py` with your changes (for example, adding a new column or table):
```python
# Example: Adding a parking spot column to UnitModel in models.py
parking_spot: Mapped[str | None] = mapped_column(String(32), nullable=True)
```

### Step 4: Run Alembic `--autogenerate`
Alembic will compare your updated `models.py` against the local database and automatically write the migration script:
```bash
alembic revision --autogenerate -m "add_parking_spot_to_units"
```

Alembic will output:
```text
Generating /path/to/backend/alembic/versions/0002_add_parking_spot_to_units.py ... done
```

### Step 5: Review the Generated Migration Script
Open the newly created file in `backend/alembic/versions/` and verify that the `upgrade()` and `downgrade()` functions match your intentions.

> **Architect Tip:** Always inspect autogenerated scripts. If you renamed a column, change `op.drop_column` + `op.add_column` to `op.alter_column` to prevent data loss.

### Step 6: Clean Up the Local Container
Stop and remove the local container:
```bash
docker stop pg-local && docker rm pg-local
```

### Step 7: Commit and Push to Git
Commit the new migration file and push to your branch:
```bash
git add backend/app/models.py backend/alembic/versions/
git commit -m "feat(db): add parking spot to units"
git push origin dev
```

### How It Gets Applied in Production
Once pushed, the **GitHub Actions CI/CD pipeline** takes over:
1. Builds the backend Docker image.
2. Triggers the **Cloud Run Migration Job** (`building-analytics-migrate-${ENV}`).
3. The job boots up **inside your Google Cloud Private VPC**, connects to Cloud SQL (`10.135.0.3`), and executes `alembic upgrade head`.
4. If successful, Cloud Run automatically deploys the updated backend web service with zero downtime.

## 🧪 Running Local Verification Tests

Run the schema integrity test suite (validates foreign key constraints, unique constraints, and cascade delete rules):

```bash
PYTHONPATH=. pytest backend/tests/test_schema_integrity.py -v
```

## ⚙️ Environment Profiles

Backend configuration is loaded dynamically via `backend/app/config.py`:
* **`backend/profile/application.yaml`**: Common baseline settings (pool size, recycle timeout, port).
* **`backend/profile/application-dev.yaml`**: Dev profile targeting `building_analytics_db_dev`.
* **`backend/profile/application-prod.yaml`**: Prod profile targeting `building_analytics_db_prod`.
* **Cloud Run Overrides**: `DB_HOST`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD` are injected automatically by Terraform and Secret Manager at runtime.
